### M8 durable fallback and rehearsals

`fetchCount` currently gates by polls-close time, fetches with `next.revalidate`, checks HTTP/parser/locality count and otherwise returns error. `ResultsStrip` only keeps old data on a thrown network exception; a successful response with `state:error` clears the displayed strip. Its retained browser state has no visible stale label. Next's documented persistent fetch cache helps but does not guarantee a validated previous count is available after malformed HTTP-200 content, deployment or cache eviction. [Vercel runtime filesystems](https://vercel.com/docs/functions/runtimes#file-system-support) are read-only except scratch `/tmp`; runtime files/module variables do not supply shared durable persistence.

Practical no-DB architecture: attempt live upstream count, fall back to a **committed validated post-close snapshot** packaged with the deployment. Store current and previous successful snapshots with election identifier, actual capture time, source URL, source `Last-Modified` if valid or `null`, payload hash and parser version; preserve unknown official update time honestly. Fresh response, stale snapshot fallback and no available data are different union states. Source time is not request/fetch time. Show stale age plus latest attempt time, counted valid votes/localities and known special-envelope coverage. Do not claim a “percent counted” without an official denominator; turnout among counted localities is not nationwide completeness. Corrected lower totals must be accepted if valid and labeled as a correction rather than silently discarded as impossible.

Important network evidence: `scripts/jobs/results-check.mts` says GitHub runners receive a CEC-CDN 404 while Vercel iad1 can reach the file. Therefore an Action should read a site's public **validated full-count snapshot endpoint**, not rely exclusively on direct runner-to-CEC access. Endpoint outputs count/provenance only after polls close. On live failure it may return fallback but must label it stale; Action only persists `fresh` validated source responses, never recirculates fallback or stamps it fresh. An unconfigured/closed/null snapshot is not test count data. No CEC pre-election placeholder enters the public page or committed production snapshot.

Action code can be prepared now without launching it. Date-gate schedule work to the count window, include manual dispatch, commit only changed count/provenance after validation and tests, and retain the previous snapshot for change comparison. Manual dispatch offers an operational backup. [GitHub schedules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) run on the default branch, can be delayed and have a five-minute minimum; snapshots are a slower durability layer, not a minute-by-minute delivery promise. Deployments add lag. An object store can improve latency but is optional infrastructure and must not be pretended configured.

Changes since previous snapshot: valid-vote and per-list vote/seat deltas from comparable election/count versions, with times displayed; unknown previous data means no invented delta. Persisted comparison is “since previous saved snapshot,” not necessarily since a reader's last minute. Browser/localStorage snapshot retention can additionally protect an already-open tab, with stale validation and expiry, but cannot replace server fallback for new visitors. Apply freshness to results page, masthead strip and any builder/home result integration so stale estimated seats never lose their label.

Required rehearsal fixtures/tests: before close; timeout; non-200; malformed header; numeric junk/negative values; missing/duplicate locality rows; valid partial count; zero denominator; absent source timestamp; envelope pseudo-locality; corrected decreasing totals; fresh → stale fallback; cold process fallback; wrong-election/invalid persisted snapshot; recover to fresh; strip receiving error JSON.
